# 配置页面以文件配置为编辑对象，热应用只覆盖可安全替换的配置项

## 背景

配置只在进程启动时加载一次，修改后必须重启；Web 界面目前只能调整上传限速与上传统计实验两组设置。本次要在 Web 界面提供一个配置页面：编辑全部配置项、保存即写回配置文件、并让能立即生效的改动无需重启。

代码事实决定了边界：`session.New` 把 `config.Config` 按值固化成不可变快照，运行期只有上传限速与实验两套可变状态，不存在"重新加载 → 应用"的编排；`api.Server` 的 token TTL、上传上限、STRM 开关与 `auth.Service` 的哈希/TTL 都在构造期固化；FUSE 与 SMB 监听只能重启。配置生成器能从 schema 渲染带注释的 TOML，但现有产物都不能回灌：`torrentfs.example.toml` 是全量默认值，`config print` 是脱敏报告。

## 决定

- 配置页面编辑**文件配置**（内置默认值叠加配置文件、尚未合并环境变量）；写回的对象是文件配置，不是生效配置。
- 保存分三段：**整体校验 → 原子写回 → 热应用**。校验失败不写盘不生效；写回未提交则文件与运行值都不变；rename 已提交但目录同步失败时新值已生效，返回"已应用"与持久化未确认，页面提示"已生效但重启后可能不保留"。这套语义沿用上传限速的既有契约。
- **热应用**只覆盖能在运行期安全替换取值的配置项；其余写入文件后标记**重启生效**。不提供进程自重启，也不提供"重启"按钮。
- 写回是**整份文件重写但稀疏**：只渲染文件层原本承载的键与本次改动的键；注释与节序由配置 schema 的生成器渲染，用户手写注释与顺序会被覆盖；写前备份。渲染器与现有生成物一样纳入 `scripts/config-docs-check.sh` 的逐字节校验。
- 来源约束：被环境变量覆盖的配置项在页面只读；secret（`password`）只读且写回时原样保留；启动时没有配置文件则页面只读；配置文件不可写则页面降级只读并解释原因。
- **热重载**与页面保存共用同一条"加载 → 校验 → 应用"路径。磁盘上的文件变化用轮询文件摘要发现（秒级）；自己写回不触发重载。
- API：`GET /api/v1/config` 返回 schema 元数据（路径、类型、枚举、默认值、文档、来源、是否可热应用、只读原因）与文件配置值；`PUT /api/v1/config` 接收稀疏 patch 与基线文件摘要，摘要不一致返回冲突。页面表单由 schema 驱动。
- 不新增功能开关：HTTP 服务开启即提供配置页面，认证边界沿用现状；影响可达性或输出形态的配置项保存前二次确认。

## 考虑过的替代方案

- 只做保存即时生效、不监听文件：外部编辑仍需重启。
- 只做文件监听：页面保存要等轮询触发，延迟与失败上报都更差。
- 逐字段自动保存：跨字段规则会让进程反复处于"半份不合法配置"。
- 最小文本改写、保留手工注释：需要自建 TOML 文本编辑，长期维护成本高。
- 独立托管文件（如 config.managed.toml）叠加：引入新的配置来源与优先级，违背 ADR-0001 的单一加载路径。
- 全量表单 PUT 或逐键 PUT：前者容易用陈旧表单覆盖别人刚写入的键，后者做不了跨字段整体校验。

## 影响

- `README.md` 的"启动时读取，修改后需重启"等表述要改写；每个配置项是否可热应用成为 schema 的元数据。
- 默认 Docker 镜像里的配置文件属 root、进程是 uid 1000，写回必然失败；需要给出可写配置位置与挂载示例，否则页面只能降级只读。
- 测试与 CI 要扩展：写回渲染器的逐字节校验、reload 的三种失败语义、API 的冲突与幂等、页面表单的 schema 驱动。
- 配置页面成为唯一写配置文件的地方；任何绕过它的运行时写入都会变成新的第二真相源。
