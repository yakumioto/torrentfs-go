# 新增分片下载接口，支持不经文件读取主动取片

> **状态**：已实现。

## 背景

torrentfs 只在有人读取文件时才取片：新加的种子连接配额为 0，没有任何管理 API 能发起下载。ADR-0003 也明确接受了"没有本地读取的内容基本不再做种"。

只通过管理 HTTP API 使用 torrentfs 的调用方因此无法让一个种子拥有可上传的内容：它能加种、分类、看统计、删种，但不能让种子取到任何分片。

## 决定

- 新增**分片下载**：`PUT` / `GET` / `DELETE /api/v1/torrents/{id}/piece-download`。请求体是半开的分片下标区间列表，与状态接口里文件的 `piece_start` / `piece_end` 同一种写法。下哪些分片完全由调用方决定，torrentfs 不做挑选，也不引入"目标比例"之类的概念。
- **一次性**：每个分片只取一次，已在缓存中的直接算完成；之后被淘汰不会自动重取，避免 tracker 上的下载量在调用方不知情时增长。
- **每个种子一个任务**：再次 `PUT` 取消并替换旧任务，请求因此幂等，不需要任务 ID。任务不持久化，进程重启后消失。
- **连接配额**：分片下载进行中视为「读取状态」，获得 `reading_conns`；任务结束后走现有的读取宽限期，再按现有规则落到上传或探针状态。ADR-0003 的分配规则与状态集合不变，只是「读取」的定义从"有打开的文件句柄"扩大为"有打开的文件句柄或进行中的分片下载"。
- **并发**：分片下载使用独立的会话级预算，所有任务合计同时最多 8 个分片，不占用播放预取的预算；第一阶段是常量，不进配置 schema。
- **超时**：任务必须有总时限，`timeout_seconds` 可选，默认 600，上限 3600，到期进入 `expired` 并保留已完成的部分。
- **缓存**：完全遵循现有缓存逻辑。分片下载取到的数据与播放数据共用同一个 LRU，不钉住、不预留、不做容量校验；请求量超过缓存容量时照常接受，先取到的分片会被后取到的淘汰。

## 考虑过的替代方案

- **复用 STRM 签名直链，由调用方发 Range 请求驱动下载**：被拒。签名链接只存在于 FUSE / SMB 输出里的 `.strm` 文件中，只有视频与光盘镜像才生成，`backend = "none"` 时不存在；即使通过 API 暴露链接，数据也要白白流经调用方一次，而且按字节读取走的是为顺序播放设计的窗口逻辑，不是按分片取数。
- **调用方直接读挂载点或 SMB 共享**：被拒。torrentfs 侧零改动，但把调用方绑定到文件输出的部署方式，无法只凭 HTTP 使用。
- **带 ID 的任务资源（`POST` 创建、按 ID 查询）**：被拒。每个种子同一时刻只需要一个任务，声明式的 `PUT` 已经足够，且天然幂等。
- **由 torrentfs 挑选分片或按字节数下载**：被拒。选哪些分片、下多少是调用方的策略，放进 torrentfs 会让执行层承担业务判断。
- **请求量超过缓存容量时拒绝**：被拒。缓存只保留一套逻辑，不为分片下载增加特例；总量控制是调用方的责任。
- **为分片下载钉住或预留缓存**：被拒。与播放共用缓存，不引入第二套保留语义。

## 影响

- 一个没有任何人读取的种子，在分片下载期间及其后的读取宽限期内可以持有 `reading_conns` 条连接；ADR-0003"空闲时连接数接近 0"的结论对使用分片下载的部署不再成立。
- 任务报告的"完成"表示分片被取到过一次，不表示它仍在缓存中。调用方需要依据运行时统计里的缓存占用自行控制请求量，否则会白白下载。
- 对已被淘汰的分片再次发起分片下载会重新下载，tracker 上的下载量随之增长。
- 并发预算 8、默认时限 600 秒与上限 3600 秒是起点，没有实测依据，实现后需要按实际吞吐调整。
